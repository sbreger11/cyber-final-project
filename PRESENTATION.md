# Intro
When you connect to a server how do you know that the server is who it says it is? How does the server know that you are who you say you are? Well, you could have an ID card to present, but the problem is that unlike a physical ID card, someone else could just copy and paste it, enabling them to imitate you. Well, then you could have a private ID card that one else could see. But, if no one else could see it, how could you ever prove that you have it? Well, that's where public ID cards come in.

From here on, replace the word ID card with key. Each entity has a public key and a private key.

Imagine person A presents their public key to person B. A is telling be "look, I am A." Person B then says to person A "Oh yeah, well prove it!" and sends person A some questions that person A could only answer correctly if they had their private key.

Assuming that there is no way to obtain the private key from the public key and that person B knows that the public key that is given to them in fact corresponds to the true person A, this encryption method is secure.

# Miller-Rabin Primality Test
We first need to find large primes. In order to do so, we use the Miller-Rabin Primality test.

Let $p$ be a prime. Let $a$ be an integer not divisible by $p$ and let $k$ be the smallest integer such that $a^k\equiv1\pmod p$. $k$ is called the order of $a$ mod $p$. Let $k=2^ab$ where $b$ is odd. Then the following is true: Either $a^b\equiv1\pmod p$ or $a^{2^tb}\equiv-1\pmod p$ for some $0\leq t<a$.

To see why this is true, simply note that that the only square roots of $1$, ie solutions to $x^2\equiv1\pmod p$ are $\pm1$  in $\pmod p$ because $p$ dividing $x^2-1=(x+1)(x-1)$ means that $p$ divides at least one of the factors.

So, since $a^k\equiv1\pmod p$, if we keep square rooting this equation while $k$ is even, we will either keep getting $1$ on the RHS until $k$ becomes $d$, or we will eventually get a $-1$ and stop. That is why the claim is true.

It turns out, that for non-primes $p$, this is only true for $\frac14$ of all possible values of $a$. Thus, if we run say $100$ such tests on a composite $p$, the probability that we would falsely get $p$ to be a prime is $\frac1{4^{100}}$.

Our code picks a large random integer (1024 bits in length) and applies this test 100 times. If it fails, we move onto the next odd integer and so on. To make our code faster, we can manually filter out things that are divisible say by the smallest 10 primes since those are very common.

# RSA Encryption
We generate two primes $p$ and $q$ and let $n=pq$. Notice that $\varphi(n)=(p-1)(q-1)$.

Now, for a public key, pick an $a$ such that $\gcd(a,\varphi(n))=1$. This can be anything reasonable, but a smallish prime number usually works well. We can manually check the gcd using Euclid's algorithm and recompute new prime numbers if this gcd happens to not be equal to $1$. We then compute the modular inverse of $a$ modulo $\varphi(n)$. This can be done in many modern libraries and simply uses the Euclidian algorithm a few times (the modular inverse is the number $b$ such that $ab\equiv1\pmod{\varphi(n)}$. We need the gcd to be 1 for $a$ to have a valid inverse mod $\varphi(n)$). $a$ and $n$ is the public key and $b$ and $n$ is the private key.

The reason that it's impossible to find the private key given the public key is because to find the inverse of $a$ we would need to know $\varphi(n)=n-p-q-1$. To do this we would need to know $p$ and $q$ and hence we would need to know how to factor $n$. Factoring large numbers like this is often computationally impossible, so the private key is secure.

If we give our public key to someone, they can send us encrypted data that they encrypted with the public key. We can prove that we have the private key by decrypting this data and sending it back, hence proving our identity. To be sure, someone can send us multiple pieces of random encrypted data to decrypt.

To encrypt data $d$ simply compute $d'\equiv d^a\pmod{n}$. To decrypt $d'$ simply compute $d'^b\pmod n$. This works because $d'^b\equiv (d^a)^b\equiv d^{ab}\equiv d^1\equiv d\pmod n$ (note that the key fact here is that $ab\equiv1\pmod{\varphi(n)}$ which allows us to get 1 after reducing the exponent mod $\varphi(n)$).

This gives us a way to verify identities. the server can verify the clients and the client can verify the server's.

# Diffie-Hellman key exchange
Now, that we know who we are communicating with, we want to exchange a secret shared key. To do this, use a safe prime number $p$. A safe prime is of the form $p=2q+1$ for another prime number $q$. In this way, the multiplicative group of modulo $p$ has size $2q$ and thus each element has an order of either $1,2,q$, or $2q$. As long as we don't pick an element of order $1$ or $2$, we can guarantee that the subgroup (a set of numbers closed under multiplication) generated by powers of that element has a lot of elements, at least $q$. These primes are available for anyone to use online.

Then, we pick a generator $g$ and share it. As long as we check that $g$ doesn't have order $1$ or $2$, it is okay to use. Finally, we choose a private number $a$ and our friend chooses a private number $b$. We share with each other $p$ and $g$ so that we can agree on them and use the same ones. Then, we share $g^a$ and $g^b$ modulo $p$ with each other. Since the subgroup is large, these values will be pretty unguessable. Each of us can then compute $g^{ab}$ modulo $p$ and this becomes our shared secret key. The hacker can not reverse engineer $a$ from $g^a$ and $g$ and $p$ because the discrete logarithm is hard to solve computationally. Essentially it is hard to find $\log_g{g^a}$ in modulo $p$ if you are only given $g$, $g^a$, and $p$.

# AES Encryption

## AES-128
 
### What is AES?
 
AES (Advanced Encryption Standard) is a symmetric cipher, meaning the same key is used for both encryption and decryption. Both sides need to already share that key before any messages are sent. That is why we do Diffie-Hellman first.
 
### Getting the Key
 
After the Diffie-Hellman exchange both sides have the same shared secret, a huge 2048-bit number. We cannot use that directly as an AES key, so we hash it with SHA-256 to get 32 clean uniform bytes, then take only the first 16 bytes.
 
16 bytes = 128 bits, which is exactly the key size AES-128 requires.
 
### Key Expansion
 
From that one 16-byte key we need to generate 11 round keys (1 initial + 10 rounds = 11 total), each 16 bytes. We work in 4-byte words and generate 44 words total, then group every 4 into one round key.
 
The pattern for generating word `w[i]`:
 
```
if i % 4 == 0:
    w[i] = w[i-4] XOR transform(w[i-1])
    # transform = rotate + sbox + RCON
else:
    w[i] = w[i-4] XOR w[i-1]
```
 
So for every group of 4 words: the first gets the full transform, and the next 3 are just plain XOR with the previous word. RCON is a round constant that ensures every group is unique even if the key has internal symmetry, preventing the key schedule from producing repeated round keys.
 
### The State
 
Our 16-byte message is arranged into a 4x4 grid in column-major order, meaning bytes fill downward then rightward:
 
```
byte 0   byte 4   byte 8   byte 12
byte 1   byte 5   byte 9   byte 13
byte 2   byte 6   byte 10  byte 14
byte 3   byte 7   byte 11  byte 15
```
 
All 10 rounds operate on this grid. Before round 1 there is also an initial AddRoundKey using round key 0.
 
### Overview of One Round
 
Each of the 10 rounds does four operations in order: SubBytes, ShiftRows, MixColumns, and AddRoundKey. MixColumns is skipped in the final round.
 
### SubBytes
 
Every byte in the grid is replaced by a fixed lookup table called the S-box (256 entries, from FIPS 197). This is the "confusion" step. It makes the relationship between the key and the ciphertext non-linear so that patterns in the input do not show up in the output. For example, `0x53` maps to `0xed`. Decryption uses the inverse S-box to reverse this.
 
### ShiftRows
 
Each row of the 4x4 grid is rotated left by its row number:
 
```
row 0: no shift      A B C D -> A B C D
row 1: shift left 1  E F G H -> F G H E
row 2: shift left 2  I J K L -> K L I J
row 3: shift left 3  M N O P -> P M N O
```
 
This is the "diffusion" step. It spreads bytes across columns so that MixColumns can then mix them together. Without ShiftRows, each column would be encrypted independently and the cipher would be much weaker.
 
### MixColumns
 
Each column is multiplied by a fixed 4x4 matrix. The result for one column `[a0, a1, a2, a3]` is:
 
```
out0 = (2*a0) XOR (3*a1) XOR a2 XOR a3
out1 = a0 XOR (2*a1) XOR (3*a2) XOR a3
out2 = a0 XOR a1 XOR (2*a2) XOR (3*a3)
out3 = (3*a0) XOR a1 XOR a2 XOR (2*a3)
```
 
The multiplication here is in GF(2^8), a finite field where every value stays within one byte. Think of each byte as a polynomial where each bit is a coefficient. So `5 = 0b00000101 = x^2 + 1`. Multiplying two bytes means multiplying their polynomials, but keeping coefficients mod 2 (so they stay 0 or 1 -- if a term appears twice it cancels out via XOR), and if the degree exceeds 7 you reduce by XORing with `x^8 + x^4 + x^3 + x + 1` (which is `0x11b`). This keeps the result within one byte.

### AddRoundKey
 
Just XOR every byte of the state with the corresponding byte of the current round key:
 
```
state[i] = state[i] XOR round_key[i]
```
 
This is where the key actually gets mixed into the data. Decryption XORs with the same key to reverse it, since XOR is its own inverse.
 
### The Final Round
 
Round 10 is identical to every other round except MixColumns is skipped. The reason is that MixColumns would just be undone immediately by the final AddRoundKey anyway, so it adds no security and would only make decryption harder to implement symmetrically.
 
### CTR Mode
 
AES by itself only encrypts exactly 16 bytes at a time. CTR mode turns it into a stream cipher that handles any message length.
 
For this you have to use a nonce. Imagine you are sending 100 messages with the same key... if you encrypted the same plaintext twice you would get the same ciphertext, and an attacker could spot the pattern. The nonce is a random 12-byte number used only once. Every encryption gets a fresh nonce so the keystream is always different even for identical messages.
 
We can do this by using this method:
 
```
for each 16-byte chunk i:
    keystream = AES(nonce + counter i)
    ciphertext chunk = plaintext chunk XOR keystream
```
 
Decryption is identical since we can generate the same keystream using the same nonce and counter, XOR again, and we get back the plaintext. No padding is needed since XOR works on any length.

## String Searching: Boyer-Moore and Aho-Corasick
 
Once a client receives messages, they need a way to search through them. We implemented two algorithms for this.
 
### The Naive Approach
 
Naive substring search slides a pattern across the text one position at a time and checks each character left-to-right. Best case is O(n) if the first character never matches. Worst case is O(n * m) for patterns like `aaab` in `aaaaaaa...` where every position requires checking all m characters before failing.
 
### Boyer-Moore
 
Boyer-Moore searches for a single pattern but scans it right-to-left inside a sliding window, which lets it skip large chunks of the text.
 
When there is a mismatch on character `c`, the bad character rule shifts the pattern so that its rightmost occurrence of `c` lines up with that position. If `c` does not appear in the pattern at all, the whole pattern skips past that spot. The good suffix rule handles cases where some characters did match before the mismatch. It shifts so the next occurrence of that matched suffix lines up. Boyer-Moore takes the max of both shifts, which is why it often jumps multiple characters at once.
 
Best case is O(n/m), which means longer patterns are actually faster. Worst case is O(n * m) for bad inputs like `aaa` in `aaaaaaa...`. In practice on natural text it is sublinear and very fast.

### Aho-Corasick
 
Aho-Corasick finds all N patterns at once in a single O(n) pass over the text instead of running Boyer-Moore N times separately.
 
A trie is a tree where each path from root to a node spells out a string. If you insert `cat`, `car`, and `dog`, the `c` node branches into `a`, which then branches into `t` and `r`. Lookup is O(length of string) regardless of how many words are stored.
 
Aho-Corasick works in three phases. First, insert every pattern into the trie. Second, add failure links using BFS: for each node, compute a pointer to the longest suffix of its current path that is also a valid prefix of some other pattern in the trie. Third, scan the text character by character, walking down the trie. On a mismatch, follow the failure link instead of backtracking to the start. The failure link guarantees you land somewhere that has already matched as much as possible, so you never re-scan any character.
 
Best and worst case are both O(n + m + k) where n is text length, m is total length of all patterns, and k is the number of matches found. It is always linear regardless of the patterns.

# Our project
Our project uses these algorithms to connect a client to a server to them allow them to send messages. After creating the client-server connection using the python socket, we verify the client and server identity using RSA (with the Miller-Rabin test used to generate the primes for it). This involves sending back and forth public keys, and then sending back and forth test data to verify identity. Our project then the Diffie-Hellman key exchange to generate a shared session key for each time the client logs on. It uses this with AES to encrypt any messages that the client wishes to send. The client also has features such as being able to search the message log with string algorithms Aho-Corasick and Boyer-Moore, as well as recieving a current list of clients connected.
